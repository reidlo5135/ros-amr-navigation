Scope and intent:
- `0.17.0` 설계문서이므로, 현재 `0.16.x`에서 확정된 recovery 구조를 기준선으로 삼고 그 위에서 `0.17.x` 목표를 설명해줘.
- `0.18.x`, `0.19.x`, `1.0.0` 방향도 로드맵/릴리즈 게이트 관점에서 반영해줘.
- 단, `0.18.x`는 더 이상 “live SLAM temp map navigation integration” 중심이 아니고, `safety + task-layer navigation operations` 중심이다.
- `0.19.x`는 더 이상 “multi-robot readiness” 중심이 아니라, `docking and deployment readiness` 중심이다.
- `1.0.0`은 fleet/multi-robot이 아니라 single-robot indoor AMR operational closure 기준으로 설명해줘.

Current architecture facts that must be reflected correctly:
- Runtime split is Nav2-like:
  - `amr_bt_navigator` decides
  - `amr_global_planner` computes global paths
  - `amr_controller_server` hosts `/amr/local_planner` and `/amr/motion_controller`
  - `amr_recovery_server` generates `wait / backup / spin` recovery commands
  - `amr_runtime_observation` aggregates operator-facing runtime summary/events
- `amr_visualization` is the in-repo ROS-native Qt6 local operator UI lane.
- `amr_mqtt_server` is the robot-side MQTT API boundary for remote clients such as `ros-rcs`.
- `navigation.launch.py` starts navigation runtime nodes, but `amr_mqtt_server` is started by `turtlebot3.launch.py`, not by `navigation.launch.py`.
- `amr_runtime_observation` currently consumes `NavigateToPoses` action feedback/status as the primary route-level action lane.

Current `0.16.x` baseline facts that must be reflected correctly:
- `planner-local escape first wiring` is effectively complete.
- `local escape-first recovery policy` has been fixed into a deterministic policy:
  - `DECISION_HARD_BLOCKED`: one local escape attempt, then `backup`, then `spin`, then fresh global replan
  - `DECISION_GOAL_PROXIMITY_BLOCKED`: skip local escape, `wait`, then re-dispatch the current plan
  - `DECISION_GLOBAL_REPLAN_REQUIRED`: skip intermediate recovery commands and go straight to fresh global replan
  - controller-owned `blocked/stalled`: deterministic `wait -> backup -> spin -> fresh global replan`
- corridor/doorway false blocked tuning has started:
  - blocked-distance-aware confirmation logic
  - `dynamic_obstacle.corridor_relax_distance`
  - `dynamic_obstacle.corridor_confirm_cycles`
- final-approach behavior has been improved enough that `0.17.x` can focus on path quality rather than emergency stabilization.

Important interpretation guidance:
- Do not present this stack as “just using Nav2”.
- Explain clearly which parts intentionally mirror Nav2 concepts and which parts are custom:
  - lifecycle split
  - BT navigator role
  - controller-server style boundary
  - runtime observation layer
  - MQTT bridge / Qt6 operator lane
- Also explain why some future steps should follow a Nav2-like maturity order:
  - `0.17.x`: planner/controller quality and path-shape quality
  - `0.18.x`: safety lane + task-layer operations
  - `0.19.x`: docking + deployment closure
  - `1.0.0`: single-robot indoor AMR operational release
