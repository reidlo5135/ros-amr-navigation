# amr_bringup

Central launch and parameter package for the AMR runtime stack.

## Main Files

- `params/amr.yaml`: shared runtime parameters
- `launch/localization.launch.py`: map server, localization, costmap server, global planner
- `launch/navigation.launch.py`: AMR runtime entrypoint

`navigation.launch.py` starts the AMR runtime by default:
- delayed `localization.launch.py`
- delayed `amr_mqtt_server.launch.py`
- delayed controller / recovery / BT navigation nodes
- delayed runtime observation and lifecycle manager nodes

## Important Parameter Groups

- `/amr/map_server`
- `/amr/localization`
- `/amr/costmap_server`
- `/amr/global_planner`
- `/amr/local_planner` via `amr_controller_server`
- `/amr/motion_controller` via `amr_controller_server`
- `/amr/recovery_server`
- `/amr/runtime_observation`
- `/amr/navigator`
- `/amr/mqtt_server`

## Launch

AMR runtime bringup:

```bash
ros2 launch amr_bringup navigation.launch.py
```

Navigation-only mode when localization and MQTT are already running elsewhere:

```bash
ros2 launch amr_bringup navigation.launch.py navigation_only:=true
```

Mapping mode:

```bash
ros2 launch amr_bringup navigation.launch.py mapping_mode:=true
```

In mapping mode, `navigation.launch.py` consumes external SLAM topics such as:
- `/slam/map/temp/refined`
- `/slam/map/temp/raw`
- `/slam/mapper/odometry`
- `/slam/mapper/pose`
- `/slam/mapper/graph_debug`

## Localization and TF Debug Guide

Expected TF ownership in localization mode:

- `amr_localization` publishes the single dynamic `map -> odom` transform.
- `robot_base_driver` publishes `odom -> base_footprint`.
- `robot_state_publisher` publishes URDF/static robot links such as
  `base_footprint -> base_link -> base_scan`.
- `amr_map_server`, `amr_costmap_server`, planners, controllers, RViz, and visualization
  nodes must not publish `map -> odom`.

Startup sanity checks before sending a navigation goal:

1. Run robot hardware bringup only, without localization or navigation.
2. Set RViz Fixed Frame to `odom` and verify `/scan`, TF, and RobotModel are stable.
3. Confirm `odom -> base_footprint` follows physical motion with:

```bash
ros2 run tf2_ros tf2_echo odom base_footprint
```

4. Start localization/navigation and set an explicit initial pose in the current map before
   sending a goal. The default config intentionally does not auto-publish `(0, 0, 0)`.
5. Watch `map -> odom` for discontinuities:

```bash
ros2 run tf2_ros tf2_echo map odom
```

6. Confirm there is one `map -> odom` authority and no duplicate localization stack:

```bash
ros2 run tf2_tools view_frames
ros2 node list | grep -E 'amcl|slam_toolbox|localization|mapper'
ros2 topic echo /tf
```

7. Send the first test goal in a wide open area, 0.5 to 1.0 m in front of the robot. Avoid
   goals on occupied or inflated cells until the map, initial pose, and costmaps are verified.

`goal_proximity_blocked` is generated by `/amr/local_planner` when a blocked pose remains on
the local plan while the robot is within `dynamic_obstacle.goal_proximity_disable_distance`
of the goal. If it appears immediately after a simple goal, check these in order:

- The initial pose matches the physical robot pose in the loaded map.
- The loaded map was built with the same LiDAR angle indexing and `base_scan` TF now in use.
- `/amr/costmap/local` does not place inflated dynamic obstacles on top of the goal.
- The goal is not inside a static obstacle, unknown cell, inflation radius, or footprint collision area.
- `goal_checker.xy_tolerance`, `planner.goal_tolerance`, and footprint/inflation settings are
  not tighter than the real map resolution and robot clearance.

After LiDAR angle or TF fixes, old maps may no longer be reusable. If `map -> odom` jumps only
when the saved map is loaded, regenerate the map with the current hardware bringup and then set
the initial pose against that new map.
